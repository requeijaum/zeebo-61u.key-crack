# Zeebo 61u.key Crack

Reverse-engineering the Zeebo console's diagnostic unlock key (61u.key) generation algorithm.

## Background

The Zeebo (MSM7201A-based console) requires a **61u.key** file on SD card (`fs:/card0/61u.key`) or internal NAND (`fs:/mcp/61u.key`) to enable the USB DIAG port. The key is:
- 14 alphanumeric characters (A-Za-z0-9), case-sensitive
- Generated by an internal TecToy tool from the console's IMEI (per TecToy insider reports; tool lost)
- Validated by Longcheer OEM code (`OEM_LCTSystemCtl.c` family) on ARM11/BREW side

## Key Findings (verified)

### Validation logic (APPS.bin 1.1.2, Ghidra decompiled)
- `check_61u_key @ 0x108d081c`: resolve mcp path → resolve card0 path →
  read both (heap `fileSize+1`, bounded) → **`strcmp(mcp_content,
  card0_content)`** → **RDevMap RPC** (the port-mapping service; §32b).
  Control flow and `strcmp` confirmed at instruction level (§30c/§30d); the
  key strings are loaded by `adr` (§30a — §2b's "no xrefs" was a tool blind
  spot, not a missing reference). ⚠ The old "SUCCESS(0,6) → event gate"
  reading is **retired** as a *local control-flow* description: nothing
  branches on `r1` here. But `r1` is not dead either — it is shipped as the
  second argument of the RDevMap RPC (§32c, corrected in §33a), so 0 vs 6 is
  real payload interpreted wherever the RPC is served. Unknown still (§32d).
  ⚠ Further narrowed in **§37b**: a census of all 22 RDevMap call sites shows
  argument 2 is **caller-dependent** — the near-clone `0x108d07a0` reports
  `4` on the same "keys matched" event where `check_61u_key` reports `6` — so
  `6` is not a shared "success/unlock" value. Argument 1 discriminates the
  caller (`r0`=0 here, `r0`=1 in the clone), not the outcome.
- **Fail-open: CONFIRMED at instruction level (§30e).** An unresolvable
  `mcp/61u.key` makes the resolve helper return `0x0d`, and `check_61u_key`
  then reports code **6** — the *same* code the strcmp-equal path reports.
  Only "opened but NULL" and "strcmp mismatch" report code 0. So removing
  `mcp/61u.key` (what the Hospital does) is enough for permanent DIAG. Still
  open: what report codes 6 vs 0 do downstream (the `0x97`/`0x10a` gate) and
  why a present non-empty internal key short-circuits (§30e-bis).
- No IMEI/serial/NV read, no crypto, no length/charset check. Keygen
  secret is TecToy-side only (provisioning code absent from firmware).
- **`arg2` decoded — it is the RDevMap *device id*, not a status code (§40a).**
  `check_61u_key` calls `rdm_assign_port(service=0, device=6)`, and device 6 is
  **"USB SER1"** in the AMSS `RDM_DEV_MAP` table (`0x17567744`, 24 entries,
  indexed by the getter `0x16E07BFA`). The near-clone calls
  `(service=1, device=4 = "USB MDM")`. So the check ends by assigning DIAG to
  USB SER1 — the literal wiki path. §37c (the interface id is a relocated
  shared-memory pointer) remains true, but it no longer blocks anything.
- The trigger for the check is **two levels up** and not yet closed (§37a):
  `0x108d081c ← 0x108d25c2 ← 0x108d2c02`, and `0x108d2c02` has exactly one
  inbound reference of any kind — a data pointer at `0x108d4f18` (Thumb-form),
  which itself has no inbound reference. Unresolved: live vtable dispatch vs
  stale descriptor.
- ARM11-only: no modem/RPC involvement (`re/notes.md` §2e).

### `usb.key` (TripleOxygen recipe) — closed on 1.1.2
The wiki's empty-`usb.key`-on-SD trick is documented for **1.1.1**. The
firmware consumer of that file on 1.1.2, `fn~0x107639da` in `fs_hotplug.c`, is
**present but unreferenced**: zero `bl`/`blx` callers in the whole APPS text
range, no PLT slot, no pointer to it anywhere in the image, and it is not a
vtable method. So on 1.1.2 the check cannot run, and creating the file is
predicted to do nothing. Two earlier claims about it are retracted: the
"vtable method" reading (no such entry at `0x11459b08`) and "path composed at
runtime" (two complete literals are used). See `re/notes.md` §36g.

**↻ §40b: a third consumer is alive — in the AT table.** `0x103611EE` does
`adr r0,"/usb.key"` and is referenced exactly once in the image: the Thumb
pointer `0x103611EF` at `0x113D0950`, which is the AT entry **`+LCTUSBDISABLE`**.
Its success path ends in `[shell+0x54](3, arg, 0x7000)` — the same port-map hook
AUXSETTINGS uses. So the hotplug path is dead, but `usb.key` itself is not: it is
reachable from AT. Open: whether `0x112A116A` opens/creates the file or only
formats it for the log.

### Open avenues (need hardware or people)
See **`HARDWARE_TODO.md`** for the full list — it is organised by access tier
(A: SD/USB only → E: needs another person), gives each test a pre-registered
prediction and a reading for *both* outcomes, and records the dependency
order. Short version:

**Top hardware test:** locked console with `mcp/61u.key` removed, to test the
confirmed fail-open (§30e) on a path that is live by reference
(`bl @0x108d2694`). The reading is now unambiguous: success = `assign(0,
USB SER1)` applied (§40a); failure = the trigger never ran (§37a) or the
assignment was overwritten. **No static blocker remains on this route.**

AT write primitive: `AT+LCTUSBLOCK="<content>"` writes the content **verbatim**
into `/61u.key` — no keygen, no derivation. ⚠ **Which partition that is, is
unresolved** (`re/notes.md` §39b): §28d's "relative ⇒ internal mcp" inference
was downgraded, because this image addresses `lctsys` under `fs:/lctsys`,
`fs:/card0/lctsys` *and* `fs:/mcp/lctsys`, and `/61u.key`'s leading `/` means
"root of the current volume", which has no file backing. If the channel *is*
reachable without DIAG, and the target turns out to be the internal key, then
writing a chosen value there plus the same on the SD defeats
`strcmp(mcp, card0)` with no keygen. Two blockers, both hardware-only: which
volume `/61u.key` resolves to, and which port carries the parser. See
`HARDWARE_TODO.md`.

**↻ §40b adds a better sibling:** `+LCTUSBDISABLE` drives `/usb.key` and the
port-map hook directly, which makes "which volume" moot — the question reduces to
"does any port answer AT before DIAG". See `HARDWARE_TODO.md` test 2b.
